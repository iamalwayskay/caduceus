Caduceus

A telemetry-free fork of T3 Code, deployed as one control surface across Kay's laptop and Haven. Hermes and DeepSeek Harness remain separate ACP providers; project files remain shared memory.

Architecture

Placement contract

Code/AI/
├── apps/caduceus/                 fork source; origin is Kay, upstream is pingdotgg
│   ├── apps/server/               orchestration, analytics removal, ACP launch
│   ├── apps/web/                  remove analytics controls/copy; retain local diagnostics
│   ├── apps/desktop/              remove outbound renderer/crash telemetry
│   ├── apps/mobile/               remove outbound traces/log export
│   ├── packages/shared/           hard-disable telemetry configuration
│   └── docs/plans/                this editable plan
└── data/caduceus/                 mutable database, logs, attachments and auth

Laptop: ~/.local/bin/caduceus → built launcher; user service points at the fork build.
Haven:  ~/Code/AI/apps/caduceus + ~/Code/AI/data/caduceus; user service runs the same commit.

Phases

1. Map and pin every network telemetry path

Classify product analytics, OTLP export, desktop/mobile reporting and developer task telemetry. Preserve local trace files, resource diagnostics, provider usage accounting, updates, model catalogs and T3 Connect transport.

Checked by: a committed inventory test fails on the untouched upstream source and names every forbidden module/config key.

2. Make outbound telemetry impossible

Delete network publishers and their settings surfaces; make configuration parsers reject or ignore telemetry destinations. Environment variables cannot turn it back on. Remove privacy copy that claims anonymous usage collection.

Checked by: focused server, web, desktop, mobile and build-tool tests plus a source scan with an explicit allow-list for local diagnostics.

3. Build the fork and replace the laptop service

Build the self-contained Linux CLI from source. Move live state from data/t3code to data/caduceus without rewriting the database, switch the service atomically, and retain the stock runtime until verification passes.

Checked by: version output, service status, existing AI project visible, no outbound telemetry connections during a real session.

4. Wire providers through ACP using CLI-owned state

Add Hermes (hermes acp) and DSH (dsh --profile acp) with absolute executable paths and DSH_HOME. Use the UI only if upstream exposes no CLI/API for provider-instance writes.

Checked by: each provider completes a read-only turn in /home/kay/Code/AI; both see the same project files.

5. Deploy the same commit to Haven and link both machines

Install the fork under Haven's AI homestead, create its unprivileged user service, then use caduceus connect link --headless on each host. No credentials are copied between machines.

Checked by: Connect status lists KPC and Haven reachable; a thread can be started on each environment.

Resolved decisions

  • Name: Caduceus. It is a one-word fork name and keeps upstream as upstream.
  • Telemetry: remove network analytics and crash/trace export. Keep diagnostics that remain on the machine.
  • Remote access: retain T3 Connect because it is functional transport, not analytics; verify its requests separately.
  • Memory: ordinary project files curated by Hermes. No memory MCP service.
  • Rollout: laptop first, Haven second; the stock T3 install remains recoverable until both pass.

Out of scope

  • Reimplementing Hermes learning inside Caduceus.
  • Copying DSH or Unsloth internals into the fork.
  • Removing update checks, provider catalogs, authentication or T3 Connect merely because they use the network.
  • Publishing mobile-store binaries in this pass.
  • Deleting the previous T3 runtime before the fork passes verification.
